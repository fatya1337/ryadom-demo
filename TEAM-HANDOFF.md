# Как объединить два проекта

## Сейчас
Команда пациента получает этот самостоятельный Next.js-проект. Команда психотерапевта работает в своём проекте. Общего выбора ролей сейчас нет. Файлы одного кабинета не надо копировать в другой по мере каждой правки. Каждая команда ведёт свой репозиторий и передаёт исходники (URL репозитория + ветка/коммит либо ZIP без node_modules).

## Чтобы объединение прошло проще
1. Оставить Next.js / React / TypeScript. Согласовывать изменения версий зависимостей.
2. UI отделять от чтения/записи данных. Пациентский адаптер — app/patient-store.ts; localStorage временный. Не обращаться к чужому browser storage для имитации интеграции.
3. Согласовать контракт: id пациента и записи, локальная date YYYY-MM-DD и timezone, текст, настроение/энергия 1–10, сон в часах 0–24. Одна запись на день обновляется по дате. created_at/updated_at — ISO UTC. Разрешить конфликты редактирования ботом и сайтом через revision.
4. Сохранить общий визуальный стиль. Пациентские CSS — с префиксом patient-; не менять глобальные button/main/h1 ради одного экрана.
5. Общей БД и миграциями управляет один ответственный. Не строить два несовместимых сервера. Бот должен писать через тот же API.

## Этап объединения
Получить финальные исходники обеих команд и сравнить зависимости. Перенести пациентские компоненты в features/patient, кабинет специалиста — в features/therapist. Разнести маршруты /patient и /therapist, вынести общий бренд/стили в shared. Заменить локальные адаптеры единым API. Вынести заметки специалиста отдельно от дневника.

После этого подключить готовую библиотеку авторизации и серверные роли. Только затем общий вход: роль выбирается при регистрации/приглашении, доступ проверяется сессией сервера. Кнопка «я психотерапевт» не должна давать права сама по себе. Сервер проверяет grant на каждом чтении и экспорте, ведёт audit_log.

Пациент создаёт одноразовое приглашение с expiry → специалист принимает → access_grant открывает историю → пациент отзывает → чтение и экспорт сразу блокируются. Согласие 18+ содержит версию и серверное время. Удаление должно затрагивать согласованный объём серверных данных.

Production: PostgreSQL/Prisma + Яндекс Клауд. GitHub Pages — только UI-демо; API на Pages не работает. Telegram/MAX требует серверной проверки пользователя, а не доверия к данным в URL.

## Финальная проверка
В разных браузерах: пациент сохраняет запись → приглашает специалиста → специалист видит ту же запись и дату → отзыв доступа блокирует историю/JSON. Проверить повторные изменения, пропущенные дни, часовой пояс, авторизацию, удаление и ошибки сети.

## Ограничения текущего прототипа
Здесь только локальное хранилище и демосогласие. Записи не отправляются специалисту. На экране «Мой специалист» показан будущий сценарий без работающих приглашений. Приложение не ставит диагноз и не вычисляет личную норму.
