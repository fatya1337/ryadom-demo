# Рядом — работа двух команд

## Что передаём
Одна кодовая база Next.js / React / TypeScript. Общий дизайн и экран выбора пространства, два независимых интерфейсных модуля. Статическое демонстрационное приложение, без настоящего входа и общей БД.

- `/` — выбор роли.
- `/#patient` — пациент; при Pages `/ryadom-demo/#patient`.
- `/#therapist` — психотерапевт.

Hash используется только для навигации статического демо, не для авторизации. Обновление страницы и кнопки назад/вперёд сохраняют выбранное пространство через URL.

## Кто что меняет
| Зона | Файлы | Владелец |
|---|---|---|
| Пациент | app/patient-workspace.tsx, app/patient-store.ts | Команда пациента / бота |
| Психотерапевт | app/therapist-workspace.tsx | Наша команда |
| Общий экран | app/page.tsx | Согласовываем вместе |
| Дизайн | app/globals.css (существующие стили), app/workspaces.css (пациент и вход) | Согласовываем вместе |
| Оболочка / сборка | app/layout.tsx, next.config.ts, package.json | Согласовываем вместе |

Пациентские стили ограничивать `.patient-workspace` или префиксом `.patient-`. Не менять общие button/h1/main ради одного кабинета. Сохранить Manrope + Prata, бумажный фон, тонкие линии, прямоугольные кнопки и сине-фиолетовый акцент.

## Уже работает
Пациент: согласие 18+ с версией и датой, запись на выбранный день, дополнение записи, шкалы настроения и энергии 1–10, сон 0–24 часа, история, точки динамики и средние за 7/14/30 календарных дней, JSON за период, ежедневный чек-лист, удаление собственных локальных данных.
Одна запись на локальную календарную дату; новая запись за ту же дату обновляет существующую. Список ритма — пример, не назначение.
Психотерапевт: реестр вымышленных пациентов, история, график, заметки, подготовка и сводка с печатью.

## Что пока НЕ соединено
Дневник пациента НЕ передаёт записи в реестр психотерапевта. Согласие на доступ в пациентском кабинете — только локальное состояние для демонстрации UX. Код DEMO-048 в кабинете психотерапевта открывает независимый пустой фиктивный профиль. Не выдавать это за рабочее подключение кабинетов.
Ни реальной авторизации, ни общего API, ни синхронизации между устройствами, ни интеграции Telegram/MAX сейчас нет. Все browser storage данные доступны коду того же origin: это не разделение прав. Не вводить реальные данные о здоровье.

## Контракт интеграции — предложение для согласования, не действующий API
`DiaryEntry` и `PatientState` описаны в app/patient-store.ts. Local adapter (loadPatient/savePatient) заменяется клиентом authenticated API; компоненты не должны знать детали PostgreSQL. Для async API добавить состояния загрузки/ошибки и дождаться успешного ответа перед сообщением «сохранено».

Согласовать с командой бота:
- `id`, `patient_id` выдаёт сервер; patient_id извлекать из сессии, не доверять клиенту.
- `date` — YYYY-MM-DD + согласованный часовой пояс пациента. `created_at`, `updated_at` — ISO UTC.
- `mood_score`, `energy_score` — целые 1–10. `sleep_hours` — часы 0–24 с шагом 0.5. Не смешивать часы с sleep_score из первоначального брифа.
- `text` — до 5000 знаков, может быть пустым при наличии шкал. API валидирует самостоятельно.
- Один день = одна запись: согласовать upsert и поведение при одновременном редактировании из бота и сайта (revision / conflict), не перетирать молча.
- PatientState.sharing не переносить в production как право доступа. Нужны отдельные access_grants и инвайты.

Предлагаемые операции:
| Операция | Результат |
|---|---|
| GET /api/me | Роль из серверной сессии, идентификатор и согласие |
| GET/PUT /api/me/entries | Свои записи / валидированное обновление за день |
| POST /api/me/consents | Версия + серверное время согласия 18+ |
| POST /api/me/invitations | Одноразовый код с expiry, без данных пациента |
| POST /api/therapist/invitations/accept | Проверить роль и код, создать grant |
| GET /api/therapist/patients/:id/entries | Данные только при актуальном grant |
| DELETE /api/me/grants/:id | Отозвать доступ; немедленно блокировать чтение и экспорт |
| DELETE /api/me/data | Серверное удаление в согласованном объёме |

Заметки специалиста хранить отдельно от дневника пациента, правила видимости согласовать. Каждый доступ/экспорт проверять сервером, фиксировать audit_log. Production: PostgreSQL/Prisma, готовая библиотека авторизации, Яндекс Клауд. Telegram/MAX initData проверяется на сервере соответствующим способом платформы; роль нельзя назначать параметром URL.

## Как работать вместе
1. Обе команды клонируют один ryadom-demo или делают fork. Команда пациента создаёт ветку feat/patient, наша — feat/therapist.
2. Меняют свои модули. Общие стили/контракт — отдельным небольшим PR для совместного просмотра.
3. Назначают одного владельца Prisma schema и миграций. Не создают две независимые БД для одного продукта.
4. Подключают оба адаптера к одному API; после этого удаляют локальные симуляции прав.
5. Проверяют: пациент → запись → код → подключение специалиста → запись и дата совпадают → отзыв → чтение и JSON больше недоступны. Затем тестируют из разных браузеров и через бот.

## Запуск
Node.js 22+, `npm ci`, `npm run dev -- --port 3000`.
Проверка: `npm run build`.
Pages: `STATIC_EXPORT=1 NEXT_PUBLIC_BASE_PATH=/ryadom-demo npm run build`.
Публикация main через .github/workflows/pages.yml. Backend в GitHub Pages не запускается.
